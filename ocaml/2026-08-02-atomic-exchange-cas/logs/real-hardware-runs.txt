Real hardware runs
==================

Everything else in this directory was produced under qemu-user emulation.
qemu-user serialises, so it validates instruction encodings and functional
correctness but says nothing about memory ordering. These runs are on real
machines with genuinely weak memory models, which is the only way the fences
actually get exercised.

Machines are donated hosts on a public compiler test farm. Identifying
details are left out on purpose.

  POWER    IBM Power10, 192 cores, Linux ppc64le
  ARM      Apple M1, 8 cores, macOS arm64
  RISC-V   SpacemiT X60, 8 cores, Linux riscv64

Both trees are built from the same checkout on each machine, one at the
baseline commit and one with the six patches applied, so the comparison is
like for like.

                   exchange tag uniqueness check across domains)

  all ok
  all ok

Emitted by the native compiler on the machine itself:

  338:	ldarx	0, 0, 5
  339:	cmpd	0, 9
  341:	stdcx.	8, 0, 5
  348:	isync
  349:	lwsync
  385:	ldarx	0, 0, 23
  386:	cmpd	0, 26
  388:	stdcx.	25, 0, 23
  395:	isync
  396:	lwsync

The trailing lwsync is the release fence required by the OCaml memory model,
which is stronger than C11 here: non-atomic stores must not be reordered
before an atomic operation. See notes/isa-references.md.

Emitted by the native compiler on the machine itself:

  472:	ldaxr	x7, [x2]
  475:	stlxr	w17, x5, [x2]
  479:	clrex
  481:	cset	x7, eq
  482:	dmb	ishst
  580:	ldaxr	x24, [x20]
  583:	stlxr	w17, x22, [x20]
  587:	clrex
  589:	cset	x24, eq
  590:	dmb	ishst

Worth noting this is the macOS variant of the arm64 backend, not Linux, so it
covers a second code path in the same emitter. The dmb ishst is the atomic
store release barrier. clrex on the failure path is not architecturally
required for an abandoned load-exclusive, but it drops the monitor rather
than leaving it marked.

Emitted by the native compiler on the machine itself:

  277:	lr.d.aqrl	a7, (a2)
  279:	sc.d.rl	a7, a5, (a2)
  312:	lr.d.aqrl	a1, (a2)
  314:	sc.d.rl	a1, s0, (a2)
  347:	lr.d.aqrl	t3, (a2)
  349:	sc.d.rl	t3, s9, (a2)

aqrl on the lr and rl on the sc is the sequentially consistent mapping. The
ISA manual warns against rl on an lr without aq, and aq on an sc without rl.
No trailing fence, because aqrl already orders both directions.


UPSTREAM TESTSUITE
----------------------------------------------------------------------------
The full OCaml testsuite, run on the patched tree on each machine.

  POWER10   1615 passed, 0 failed, 0 unexpected errors
  RISC-V    1615 passed, 0 failed, 0 unexpected errors
  ARM       1613 passed, 1 failed, 0 unexpected errors

The single failure on the ARM machine is tests/native-debugger/lldb.ml, which
is an lldb output format mismatch on that host and nothing to do with this
work. The unmodified baseline tree fails it identically on the same machine,
so there is no regression. That test is skipped on Linux, so it only ever
shows up on macOS.


WHAT THIS DOES AND DOES NOT SHOW
----------------------------------------------------------------------------
Shows: the sequences assemble, execute, and give correct results under real
concurrency on two weakly ordered architectures, including the LL/SC retry
loops under genuine contention.

Does not show: that the fences are minimal. A missing fence would likely
show up here eventually; an unnecessary one would not show up at all. The
argument for each fence being the right one rests on the ISA documents and on
matching the conventions already accepted for fetch-and-add.
