Real hardware runs.

The qemu-user runs in qemu-and-native-runs.txt cover encodings and logic but
not ordering, because qemu-user serialises. These are the ones that put the
fences under real weak memory ordering with real concurrency.

Hosts are donated machines on a public compiler test farm, plus a community
mainframe instance. Each built the same tree from the same checkout, cloned
straight from the fork branch with the patch applied on top.

  ppc64le    IBM Power10, 192 cores
  riscv64    SpacemiT X60, 8 cores
  s390x      z15, 2 cores

Power is the interesting one for this change, because ldarx now reads straight
into the result register instead of going through r0, and because 192 cores
lets the reservation actually get stolen. RISC-V is the other one, because the
sc status moved off the result register onto t1 and the loop had to stay inside
the constrained LR/SC limits.

z/Architecture is strongly ordered and CSG serialises on both sides anyway
(SA22-7832 page 7-159), so s390x carries the least ordering risk of the three.
The change there is a pure deletion, and this is that deletion running on the
real machine.


================================================================
arm64
================================================================

No arm64 host in this set, so arm64 is qemu only. Its change is the same shape
as the s390x one, a deletion of the cset at the end. The arm64 emitter
self-checks instruction lengths at assembly time, so a wrong size table entry
fails the build rather than miscompiling, which covers the size change but not
the ordering.
